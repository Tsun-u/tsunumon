   - **Everything else** (fade, slide, reveal, stroke-on, projectile paths, force diagram reveals) → GSAP (pre-loaded)
   - **Simplest effects** (pulse, highlight) → CSS `@keyframes` with `animation-duration` matching `estimated_duration_sec` and `animation-fill-mode: forwards;`

   Principle: if the slide already uses a JS diagram library, animate with that same library's built-in transitions. GSAP is for slides that don't use a diagram lib, or for effects the diagram lib can't do (stroke-on reveals, motion paths).

   **GSAP Usage Guide:**
   GSAP and plugins (MotionPathPlugin, DrawSVGPlugin) are available globally. Put animation code in a `<script>` tag at the end of slide_html. Total animation must complete within `estimated_duration_sec`.
   ```html
   <script>
   document.addEventListener("DOMContentLoaded", function() {
     const tl = gsap.timeline();
     tl.to("#element", { x: 100, y: -200, duration: 2, ease: "power2.out" })
       .to("#label", { opacity: 1, duration: 0.5 }, "-=0.5");
   });
   </script>
   ```
   GSAP adds visual effects to elements that already exist in the DOM — it animates, it does not compute geometry. Build the diagram with a JS library first, then layer GSAP effects on top.
   Common patterns:
   - **Stroke-on reveal** (paths, arrows, flows): `gsap.from("#path", { drawSVG: "0%", duration: 3 })`
   - **Sequential highlight** (step-by-step callout, code trace): Sequential `.to()` calls changing opacity/color
   - **Motion along a path** (ball following a pre-drawn arc): `gsap.to("#ball", { motionPath: { path: "#arc" }, duration: 3 })`
   - **Fade / slide entrance**: `gsap.from("#card", { opacity: 0, y: 30, duration: 0.8 })`
   Rules: Always wrap in `DOMContentLoaded`, use `gsap.timeline()` for sequences, set explicit `duration` on every tween, use SVG for paths/shapes, keep total duration at ~80% of `estimated_duration_sec`, do NOT call `gsap.registerPlugin()` (pre-registered)

   **Animation priority order** (always start from #1 and only fall through when the higher option genuinely cannot express the visual):
   1. **Math equations / geometry** → JSXGraph built-in animation (`board.animate()`, element transitions) — coordinates are always correct
   2. **Science / physics phenomena** (pendulums, energy diagrams, cell processes, circuits, waves) → D3.js transitions (`.transition().duration(1000).attr(...)`) — computed positions stay correct during animation
   3. **Visual effects only** (fade, slide, reveal, stroke-on for elements already rendered by a JS lib or as static HTML) → GSAP
   4. **Raw SVG + GSAP** → Only when no JS library in the routing table can express the visual (e.g., a custom decorative animation with no geometric relationships). This is rare — most physics/science diagrams fit D3.

   **Figure-text consistency check**: Before finalizing any diagram, scan the narration for directional claims and verify the diagram matches. This applies to all rendering methods (JS lib or hand-written SVG).

   **Mathematical function plots** (parabolas, sine waves, error curves, distributions): **ALWAYS use function-plot.js** — never draw with SVG paths. function-plot.js handles Cartesian coordinates correctly and prevents vertex/curve inversion bugs. Example:
   ```html
   <div id="plot" style="width:860px;height:380px;margin:0 auto;"></div>
   <script>document.addEventListener("DOMContentLoaded", function() {
     functionPlot({
       target: '#plot', width: 860, height: 380,
       xAxis: { domain: [0, 10], label: 'Model Complexity →' },
       yAxis: { domain: [0, 1],  label: 'Error' },
       data: [
         { fn: '0.8 / (1 + 0.3*x)', color: '#3498db', title: 'Training Error' },   // monotonically decreasing
         { fn: '0.8 / (1 + 0.5*x) + 0.02*(x-3)^2', color: '#e74c3c', title: 'Test Error' }  // U-shape
       ]
     });
   });</script>
   ```
   You still have full creative freedom to animate with GSAP for physics trajectories, vector diagrams, force fields, circuit flows, chemistry pathways, pendulums, etc. — use the right tool for each visual.

   **If raw SVG is unavoidable** (no JS library matches — see rendering decision rule above), sanity-check the y-axis direction before locking in coordinates:
   - SVG `y=0` is visually at the TOP of the canvas; larger y appears LOWER on screen.
   - Chart convention: top = LARGER value, bottom = SMALLER value.
   - So a "high" value → SVG y SMALL (near top); a "low" value → SVG y LARGE (near bottom).
   - **Decreasing function**: SVG y goes SMALL → LARGE (visually the line drops).
   - **U-shape / valley**: SVG y goes SMALL → LARGE → SMALL (dips and comes back up).
   - **Inverted U / mountain**: SVG y goes LARGE → SMALL → LARGE (rises and falls).
   - Before writing control points, note `"at x=X, value = HIGH/LOW → SVG y = SMALL/LARGE"`, then fill in numbers and re-read once more.
